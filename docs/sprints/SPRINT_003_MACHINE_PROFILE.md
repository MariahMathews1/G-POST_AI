# Sprint 3 — Machine Profile foundation and manual review

Machine Profile is a human-reviewed engineering worksheet for one saved Machine. It organizes information that may later support Post development. This sprint provides manual entry and review only. No example engineering values are seeded into a real Machine.

## Definitions and saved values

The shared catalog is [`backend/app/machine_profiles/definitions.json`](../../backend/app/machine_profiles/definitions.json). It contains **43 definitions** in five categories:

1. Machine & Controller
2. Kinematics & Limits
3. Modal Rules & Commands
4. Cycles & Machine Behavior
5. Safe Start / Header / Footer

A definition describes the information: key, name, help text, category, value type, allowed units, machine types, normal importance, display order, and optional future use. Change this file to add or adjust definitions using existing value types. The React editor uses that metadata rather than a custom field for each definition. Adding a new value type requires a corresponding input and backend validation. Keep definition keys stable; changing a key does not rename saved data.

A **ProfileFact** is one Machine's value and review decision for a known definition. Migration `003_create_profile_facts.sql` adds the `profile_facts` table to the existing SQLite database, normally `backend/data/companion.sqlite3`. The unique Machine ID + fact key prevents duplicate entries. Saving information updates the same row when it already exists. Nothing is saved for an untouched, missing definition.

Values are stored as JSON inside that row: text, numbers, choices, lists, or simple rotary-axis objects. JSON keeps the small schema flexible; the API validates values against the catalog before saving. Lists use one item per line in the editor. Rotary-axis entries contain A/B/C, minimum and maximum angles in degrees, and a continuous-rotation flag. No advanced kinematics or unit conversion exists.

## Review and provenance

| Editable status | Meaning |
| --- | --- |
| MISSING | No usable value exists. |
| NEEDS_REVIEW | A value has been entered and awaits acceptance. This is the manual default. |
| CONFIRMED | The engineer deliberately accepted the value. |
| NOT_APPLICABLE | The information does not apply to this configuration. |

New or changed information defaults to Needs Review. Changing a confirmed value, unit, or source/notes in the editor returns it to Needs Review. Select Confirmed after completing the review. Saving Missing or Not Applicable clears the value and unit; notes and provenance can remain. Empty information cannot be confirmed. There are no confidence scores.

Every saved fact retains source type, optional source document, source location/page, engineering notes, and created/updated timestamps. The source is **PROGRAMMER_ENTRY** unless the engineer explicitly chooses an existing uploaded Document, which makes it **DOCUMENT_REFERENCE**. The Document must belong to this Machine. Archived documents remain valid references because archive preserves records and original files. Dates are generated by the backend; saving preserves the original creation time.

Manufacturer, model, Machine type, and controller description are **MACHINE_RECORD** values. They are read live from the Machine table and have no duplicate ProfileFact row. Their detail view links to Edit Machine. Controller Model displays the existing combined controller description; controller manufacturer and series/version remain separate manual information without attempting to infer them.

Inherited identity has no editable review status. It displays “Machine record” and is excluded from review counts rather than being silently confirmed. The summary counts confirmed and pending editable values, plus missing information that is applicable and normally important. Not Applicable is never missing. Each category displays confirmed / eligible editable information; inherited and Not Applicable rows are excluded from that denominator. Optional rows can appear without increasing the Missing summary.

## Applicability and archive behavior

Catalog applicability uses the existing Machine type names (`Mill`, `Lathe`, `Mill-Turn`, `Swiss`, `Other`) or `ALL`. A basic Lathe and Swiss worksheet omit Y and rotary definitions. Mill and Mill-Turn show Y and rotary information; rotary definitions are optional. Threading cycles normally appear for Lathe, Mill-Turn, and Swiss. These are initial display defaults, not machine capability conclusions. Engineers can mark displayed information Not Applicable.

After a Machine type change, previously saved information remains visible with an applicability notice, so it can be reviewed or marked Not Applicable. It is not silently discarded, and an inapplicable missing row does not increase Missing. Unsaved inapplicable definitions are omitted from the normal worksheet. More detailed machine configuration rules are outside this sprint.

Archived Machines retain readable and editable profiles, matching the existing Machine and Document archive behavior. Archive is not deletion. The unsaved `/machines/demo` example cannot store a profile.

## Interface and API

The existing Machine Profile tab has a compact review summary, Search profile alongside disabled Find Information, and five collapsible sections. Each row shows only Information, Value, and Status, with subtle hover/focus treatment. Clicking a row or its keyboard-accessible fact button opens a focused editor with a 900px maximum width. Its header has a back action, fact name, category, and description. One form container groups Profile Value, Source / Basis, Engineering Notes, and read-only Future Use metadata. Numeric values and units sit together; status and source-location controls use restrained widths. Inherited facts have a compact read-only view and Edit Machine action. Cancel preserves saved information. Successful Save refreshes the summary and returns to the category. Find Information is disabled with a future-extraction explanation.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/profile-definitions` | Read the shared category/definition catalog. |
| `GET /api/machines/{id}/profile` | Read applicable definitions, live inherited values, saved facts, and summary. |
| `PUT /api/machines/{id}/profile/facts/{key}` | Validate and save one known editable fact; return the updated profile. |

Backend files live in `backend/app/machine_profiles/`: `catalog.py`, `definitions.json`, `schemas.py`, `service.py`, and `routes.py`. Frontend files are `types/machineProfile.ts`, `api/machineProfiles.ts`, `features/machineProfiles/FactEditor.tsx`, and the replaced `features/machines/tabs/MachineProfileTab.tsx`. Database startup and Machine workspace wiring reuse the existing architecture. Dashboard, Machines, and Documents keep their existing layout.

## Future extraction and Post development

```text
Implemented now:
Known definition -> Manual engineering entry -> Needs Review
                 -> Deliberate human confirmation -> Machine Profile

Future only:
Machine / Controller Documents
    -> Deterministic extraction
    -> ProposedFactCandidate (value + document + page + evidence)
    -> Human review / Apply
    -> ProfileFact / Machine Profile
    -> Post development
    -> OFG / FIL assistance
```

A future **ProposedFactCandidate** must remain separate from a **ProfileFact**. Extraction may propose a value without overwriting the worksheet. A human reviews it and applies an explicit decision before it becomes accepted engineering information. No candidate table, extraction service, or Apply pipeline is implemented now.

Future Use is explanatory definition metadata only. It does not configure OFG, map values, create a Post, or generate FIL. Profile facts contain machine-level engineering information only: no CL/NCL, part geometry, or production NC programs. No G-code is generated. Sprint 3 makes no Azure OpenAI or external generative AI calls and includes no OCR, extraction, RAG, machine learning, simulation, or compilation.

## Verification and manual acceptance

**133 backend tests pass**, including 37 new profile checks for catalog metadata, applicability, live inheritance, default review, explicit confirmation, Missing/Not Applicable, summary counts, unique updates, typed validation, document ownership, Machine isolation, archive behavior, and restart persistence. Existing Machine/Document migration tests now expect version 3 and the added table.

**77 frontend tests pass**, including 17 profile UI/API checks for category display, inheritance, direct row/keyboard editing and Edit Machine navigation, numeric/choice/list/rotary inputs, review transitions, cancellation, provenance, source loading/retry, errors, and reloading saved information. Lint, typecheck, and production build pass.

Live HTTP acceptance used a separate temporary database: manual entry, document provenance, explicit confirmation, Not Applicable, summary updates, re-fetch, and an actual backend process restart preserved values and provenance. The real frontend proxy and saved-Machine route responded successfully; no test facts were written into the user's Machine records.

No browser was available from the browser tool. Automated DOM tests and live HTTP checks do not establish mouse-driven visual acceptance or an observed browser refresh. To inspect the finished workflow:

1. Open the existing frontend URL, then Machines and a saved Machine.
2. Open Machine Profile and expand each category. Check identity against Overview.
3. Find a fact in its category or with Search profile. Click it, enter a reviewed test value and notes, and save with Needs Review.
4. Reopen it, deliberately choose Confirmed, and save. Check summary/category counts.
5. Reference one of that Machine's uploaded Documents and enter its page/location.
6. Mark another fact Not Applicable; confirm Missing decreases and no value remains.
7. Refresh and reopen the editor to inspect values, source, notes, and dates.
8. Confirm Find Information remains disabled and Add Information is absent.

The Sprint 3 UI refinement removes the inline Add Information selector and its three state variables. No separate selector component or route existed. The Profile tab, FactEditor, scoped profile styles, and affected frontend tests were updated; backend definitions, models, persistence, and APIs were unchanged. The refined header moves count explanations into accessible descriptive text instead of a prominent paragraph. Status treatments remain restrained and neutral where appropriate.

Sprint 3 stops here. No Sprint 4 work is included.
